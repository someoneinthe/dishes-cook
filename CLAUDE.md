## Claude Code notes

- **Product**: an Android-first app (iOS later) that suggests what to eat from the recipes the user has saved. Data is local-first: the phone's database is the source of truth, optionally synced with the user's own self-hosted server (see `docs/sync.md`); the sync is the only network code. Don't add other backends, accounts, analytics or network calls without asking. Any change to what the app stores or sends also updates the About page (`about` in `src/i18n/en.ts` and `fr.ts`, see CONTRIBUTING.md).
- **Before saying a task is done**: run `npm run check` (it also runs before every push). When SonarQube Cloud fails a PR on a rule `npm run lint` didn't flag, run `npm run lint:sonar-rules` (CONTRIBUTING › Code quality) instead of adding the rule by hand. Run `npm run doctor` too after touching dependencies or `app.config.ts`. After editing a `*.feature` file, run `npm run docs:features` (regenerates `docs/features.md`); after changing `src/db/schema.ts`, run `npm run db:generate -- --name <change>` (adds a migration and regenerates the diagram in `docs/database.md`). Migrations are additive: never edit or delete a merged one (`frozen-migrations.test.ts` fails), never reset users' data; see `docs/database.md` › Changing the schema. CI fails when either page is out of date.
- **Check every user-facing change end to end on a phone AND on a TV before shipping it** (before opening the PR or calling it done), each on an emulator or a real device: run it with `/run-android` and go through the changed flows. On the phone: create, edit, delete, navigate away and back. On the TV (`Television_1080p` emulator or a real TV, driven with the D-pad only): the same screens read-only, every control reachable and showing the focus ring, Back returning the focus to what opened the screen. A launch alone doesn't count. Jest runs on Node, not Hermes: `Array.prototype.toSorted` passed every test and crashed the app on launch. Check both languages (Settings › Language) and both themes, switching light/dark **while the app runs** (`adb shell cmd uimode night yes|no`): a cold start or a font-size change restarts the app and hides bugs that only show on a live change (Unistyles' adaptive themes stayed one switch behind until PR #58). Report what you checked on the phone and on the TV, and anything you couldn't check. The Maestro flows (`.maestro/`, `npm run test:e2e` on an end-to-end build) automate the phone's recipe and sync basics: extend them when those flows change, but they don't replace looking at the screens. When a flow fails because something is hidden or out of reach (behind the keyboard, off screen), it's a bug users hit too: fix the app, don't make the flow scroll or tap around it.
- **Lists load at most 50 rows per query, with pagination**: never read a whole table into a screen. Use `usePagedQuery` (keyset pages of `PAGE_SIZE` = 50, infinite scroll, `MAX_PAGES` kept in memory) with a `(sort_key, id)` index, and `LIMIT` any other list query (suggestions, pickers). Counts and random picks are done in SQL, not by loading ids. Data goes through TanStack Query; writes go through Drizzle, which invalidates the queries. See `docs/database.md`.
- **Sorting, filtering and ordering MUST happen in the data layer, never in the front**: in SQL (`ORDER BY`, `WHERE`, `LIMIT`) in `src/features/*/db/*-queries.ts` today, in the API when there is one. Screens, hooks and components display rows in the order they come, as they come: no `.sort()`, `.filter()`, search or ranking on fetched data. Paginated results can't be sorted or filtered correctly after the fact anyway. Editing local UI state (e.g. removing an item from a form's selection) isn't data filtering.
- **Always confirm deletions**: every removal (recipe, ingredient, anything added later) asks first, with `useConfirmDelete` (`src/components/use-confirm-delete.ts`). ESLint refuses destructive dialog buttons elsewhere.
- **UI text is translated (EN + FR)**: never write user-facing text (JSX text, labels, hints, placeholders, alerts) in a component; add it to `src/i18n/en.ts` **and** `src/i18n/fr.ts` (TypeScript fails if French is missing an entry) and read it with `useMessages()`. Names and counts go through functions (plurals differ: French uses the singular for 0). Check new screens in both languages (Settings › Language). User content in the database is never translated.
- **The keyboard never hides the field being typed in**: the root layout (`src/app/_layout.tsx`) wraps every screen in a `KeyboardAvoidingView`, because Android draws the app under the keyboard (edge to edge) and doesn't always shrink the screen itself: the emulator's Gboard does, SwiftKey on a Pixel 9a didn't, so the emulator never showed the bug. Don't add a screen-level one (it would add its own padding). Content shown under a field (suggestions) needs the field scrolled up on focus (the ingredient search does). Check changes to text fields or keyboard handling on a real phone, not only the emulator.
- **Text follows the phone's font size** (accessibility): sizes come from `theme.typography` in dp, which React Native scales with the system font setting. Never set `allowFontScaling={false}` or `maxFontSizeMultiplier`, never give text containers a fixed `height` (use `minHeight`), let rows wrap (`flexWrap`) instead of squeezing text, and size icons with `useIconSize` so they grow with the text. Check new screens at a large font: `adb shell settings put system font_scale 1.3` (and `2.0`), then back to `1.0`.
- **Android TV** (same APK): `isTv` (`src/lib/device.ts`) makes the app read-only there (no add/edit/delete, no Ingredients entry) with the menu always on the left (`src/components/tv-menu.tsx`). Every pressable shows the D-pad focus: `Button`/`Chip`/segments already do; a new bare `Pressable` (list row…) uses `useFocusRing`. The TV check of every user-facing change (see above) is done on the TV emulator, which is enough for most changes; a real TV only when the maintainer asks for it, or for what the emulator can't show (the launcher entry and banner, a real remote).
- **Buttons** (always `Button`, never a bare `Pressable` styled as a button):
  - **Colors**: the primary action is blue with white text (`variant="primary"`, default); a deletion is red with white text and always an icon (`variant="danger"`, `icon="trash-can-outline"`, required by the types); other actions are outlined (`variant="secondary"`), lightly tinted blue while their option is on (`variant="active"`, e.g. Filters with filters applied).
  - **Icon only when the icon speaks for itself** (+ add, ✏️ edit, 🗑 delete, ✓ save, ✕ cancel, 🛒 add to list, 👁 open a recipe (`eye`)): `isIconOnly`, the `label` stays for screen readers. **Icon + text** when the icon alone isn't enough (e.g. 🎲 Suggest), **text only** when no icon fits. This holds in cards and rows too (the meal choice's suggestion: 🛒 and 👁 only).
  - **Text vs icon is the `Button`'s job, never the screen's**: an `isIconOnly` button shows its text only with Settings › Show button labels, and always in a ⋮ menu; `Button` does both (`usePreferences().isShowingButtonLabels`, `MenuContext`). Never show or hide a label yourself (no `isShowingButtonLabels` in a screen, no `<Text>` next to a button), never pass a label meant to be seen on an icon button, and don't give a button two looks for phone and TV. `isLabelAlwaysHidden` only where the text has no room.
  - **Screen actions go in the header**, top right: `<Stack.Screen>` / `<Drawer.Screen options={{ headerRight }}>` with `headerActions(buttons, more)` (`more` goes in ⋮ when the header has no room). A recipe's page puts all its actions in ⋮, labeled (`headerMenu(buttons)`). Actions on one item (a list row, a card) stay in it. Don't remove a button because another one does the same: ask.
  - **In doubt, ask before building**: whether a button is icon-only, icon + text, in the header or in ⋮, which icon, which variant, or what it does on a TV. Ask the maintainer (with a preview of each option) rather than picking and having it fixed later.
  - Icons: `src/components/icon.tsx` (Material Design Icons); colors: `actionPrimary` / `actionDanger` / `onAction` tokens (selected controls — segmented choices, chips, active menu entry — use the same blue).
- **Formatting is automatic**: a PostToolUse hook (`.claude/hooks/format-file.sh`) runs ESLint `--fix` + Prettier on every file you write/edit. Don't hand-format.
- **Dependencies**: always `npx expo install <pkg>`; justify any new dependency in the PR description.
- **Sync server files** (`server/migrations`, `server/hooks`): a new server migration also goes in `SERVER_MIGRATION_LIST` (`src/features/sync/server-version.ts`, tested). Once a PR changing `server/` is merged, deploy it with `npm run server:deploy` from an up-to-date `main` (`SYNC_SERVER_SSH` set): until releases exist, nothing else updates the server, and phones refuse to sync with a server older than their app. See `docs/sync.md` › Versions and › Updating the server.
- **Generated / release-owned files — never edit by hand**: `android/`, `ios/`, `CHANGELOG.md`, `.release-please-manifest.json`, and the `version` field in `package.json` (release-please owns them).
- **Commits & PRs**: Conventional Commits; the PR title is the squash commit and drives the version bump (`feat` → minor, `fix` → patch). Branch from `main` as `feat/…`, `fix/…`, `chore/…`.
- **Never merge, always rebase**: never bring `main` into a branch with a merge commit (no `git merge main`, no default `gh pr update-branch`). Rebase instead (`git rebase origin/main` then `git push --force-with-lease`, or `gh pr update-branch --rebase`). Force-push only feature branches, never `main`.
- **Assign PRs to the author**: always open PRs with `gh pr create --assignee @me`.
- **Expo APIs change every SDK**: check the versioned docs for the installed `expo` major (see above) instead of relying on memory.

## Project skills

- `/new-feature <name>` — scaffold a feature folder, screen, route and test.
- `/run-android` — build, install and run the app on an Android emulator, screenshot and inspect it.
- `/add-dependency <pkg>` — add a package the Expo-compatible way and validate it.
- `/upgrade-expo-sdk` — upgrade to the next Expo SDK.
- `/release-status` — what the next release will contain and whether it's ready.

Agent `convention-reviewer` reviews a diff against the conventions in `CONTRIBUTING.md`.
