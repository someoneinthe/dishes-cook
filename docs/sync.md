# Server sync

The phone's database is the source of truth: the app works the same without a server. Optionally, it syncs with **your own [PocketBase](https://pocketbase.io) server**, so several phones share the same recipes.

## In the app

**Settings › Data storage**: _This device only_ (the default) or _Synced with a server_. To connect, type the server's address and the email and password of an account created on the server. The phone signs in and keeps only the sign-in token (in `expo-secure-store`), never the password.

- **First sync merges**: the phone's recipes and the server's are combined. An ingredient with the same name on both is one ingredient (see [ids](#ids)); two different recipes with the same title stay two, one of them numbered (see _Same-title recipes_).
- **When it syncs**: when the app starts or comes back to the foreground (unless the last sync worked less than a minute ago and nothing waits to be sent), 5 seconds after the last change (a burst of edits makes one sync), and with _Sync now_. What a sync writes itself (the rows it pulls) doesn't call for another sync, and screens refresh once, at its end. Code: `src/features/sync/use-auto-sync.ts`.
- **When the server can't be reached** (away from home, server down), the sync fails quietly: Settings shows it, and the next sync catches up. Nothing is lost: changes stay on the phone until they're pushed.
- **Sync status in the header**: the menu's screens (except Settings) show an icon at the top right while changes wait to be pushed (cloud with an arrow, read as "3 changes to sync"; it also shows for the few seconds before the sync that follows an edit) or when the last sync failed (cloud with an exclamation mark, read with the number of changes waiting). It opens Settings scrolled to Data storage, which tells why (on a TV, the remote's focus goes to _Sync now_, and Back brings it back to the icon). Hidden when everything is synced, or without a server. The waiting changes are counted in SQL: the deletions, and the rows the server doesn't have in their current version (see _Server versions_ below), read from the partial `*_to_push_idx` indexes. Code: `src/features/sync/use-sync-status.ts`.
- **Stopping the sync** keeps the recipes on the phone and on the server. Connecting again merges them again. A sync running at that moment stops at its next request and keeps nothing (sign-in token, progress), so it can't bring the server back, nor mix it up with one connected to right after.
- **A phone restored from a backup** has the server's address but not the sign-in token (encrypted with a key that stays on the old phone): Settings says the server refused the sign-in, and connecting again fixes it.
- **Meal history** syncs too: each time a recipe was cooked (Meal choice or a recipe › _I cooked it_), and the times removed. Marking a recipe as cooked doesn't change the recipe, so it isn't sent again and can't overwrite an edit made on another phone.
- **Recipe photos** sync too, as a protected file on the recipe (only signed-in phones can download them, with a short-lived file token). A photo goes up after its recipe, in a request of its own (multipart, `@jsonPayload` for `modified`), and comes down after the pull; at most 20 each way per sync, the next sync carries on. A photo waiting to go up counts as a change waiting.
- **Menu › About** tells people what syncs and with whom: a change to the synced data (a new field or table) updates it too (`about` in `src/i18n/en.ts` and `fr.ts`).

## How it works

`synchronize` (`src/features/sync/sync-engine.ts`; the steps in `sync-pull.ts`, `sync-push.ts` and `sync-photos.ts`) runs in two steps:

1. **Pull**: the rows written on the server since the last pull (`updated >= cursor`, one cursor per table), ingredients first since recipes link to them, then the meal history (`cooked_meals`), which links to recipes, in pages of 50 that follow each other by key (after the previous page's last `(updated, id)`, not by page number: a row written during the pull moves to the end instead of shifting the next pages). A pulled row replaces the phone's only if it's newer. A recipe using ingredients the phone doesn't have yet (another phone pushed both during the pull) gets them once the ingredients are pulled again, in the same sync; a meal of a recipe the phone doesn't have yet waits for the recipes to be pulled again, and is dropped if its recipe still isn't there (deleted). At most 200 pages per table and per sync: the next sync carries on.
2. **Push**: the deletions made on the phone, then the rows the server doesn't have in their current version (ingredients, recipes, meals: `server_version is not updated_at`, read on the partial `*_to_push_idx` indexes, which hold only those rows), in pages of 50.

| Rule                  | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Newest change wins    | Each row carries the time of its last change (`updated_at` on the phone, `modified` on the server, in ms). A pulled row keeps its `modified` as `updated_at`, so it isn't pushed back. The server refuses an update older than what it has, and one of the same version that changes anything but the recipe's photo (update rule since `1792900000-same-version-unchanged.js`: newer `modified`, or the same with every field the phones send unchanged): an app sending back what the server has goes through, as does a photo uploaded onto the version just pushed. It also refuses a `modified` more than a day ahead of its own clock (`server/hooks/modified-limit.pb.js`, a 400, before anything is stored): saved, such a row could never be changed or deleted again. The refusal is temporary: the same push goes through once the server's clock is within a day of it.                                                                                                                                                                                                                                                                                                                                                                                |
| Whole rows            | A recipe is one row, its ingredients included (a list of ingredient ids on the server, and their quantities in `quantities`, normalized like on the phone: `{ "<ingredient id>": { "amount": 500, "unit": "g" } }`, no unit = pieces; a quantity pulled in another unit is normalized on arrival). Two phones changing the same recipe between syncs keep both changes: see _Changes on two phones_.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Changes on two phones | Each recipe keeps the content the server has in its `server_version` (`recipes.synced_content`, `SyncedContent` in `src/features/sync/recipe-merge.ts`), set with `server_version` by a pull and by a saved push. When a pull brings a recipe the server changed since (a newer `modified` than its `server_version`) and the phone changed it too (`updated_at` ≠ `server_version`), the pull merges them field by field from that content: each field (title, text, season, course, kind, times) takes the side that changed it, and the newest side (by `updated_at` / `modified`) when both did. Ingredients merge one by one by sync id (in this phone's terms: an alias's ingredient under its own id): added on one side, removed on one side, or a quantity changed; an ingredient the phone doesn't have yet stays as the server has it. The merged recipe gets a version newer than both and goes back to the server in the same sync (unless it's the server's version: the phone's changes were already there). A photo taken or removed here stays through a merge; otherwise the server's comes. Without that content (a recipe changed here before this app version and not synced since), the newest change wins, whole, as before.                |
| Meal history          | One record per time a recipe was cooked: `recipe` (the recipe's sync id) and `cooked_at` (ms). Only created and marked `deleted`, never changed. A recipe's meals go with it: deleted with it on each phone, while the server keeps them, unused. A recipe deleted on a phone and brought back by a newer edit from another one gets its meals back: when a pull adds a recipe the server had before the phone's last pull of meals, every meal is pulled again.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Photos                | The phone keeps three names (`recipes.photo_file`, `photo_synced`, `photo_pending`): its file, the server's name of that same photo, and the server's name of a newer one to download. A photo taken here (`photo_synced` empty) is uploaded; one whose file has gone missing before its upload is forgotten. Each recipe version the phone pushes clears the server's photo in the same request, unless the server's photo is the one the phone shows or is about to download: a removed or replaced photo never outlives its version on another phone pulling in between (a new photo is uploaded right after, onto that version). A pulled recipe whose photo differs keeps the phone's until the new one is downloaded. Uploading a photo doesn't change the recipe's `modified`, so a pull of the same version still compares its photo; a photo removed is always a new version. Files no recipe uses any more are deleted at start.                                                                                                                                                                                                                                                                                                                         |
| Authors               | A recipe's `created_by` is the server account that created it, set by the server (`server/hooks/recipe-author.pb.js`) whatever a request sends, and never changed by a phone (the admin may change it). The app never sends it: it pulls it into `recipes.created_by`, even from a row it has a newer version of (the author isn't part of the version). Until its first push, a recipe has none (null), and counts as the phone's own. The phone keeps its account's id (from signing in and each token renewal), for the _Added by: Me_ filter of Recipes and Drinks (shown only when synced): the account's recipes and those not on the server yet. The recipe's page shows who added it by the account's name (_Added by Alice_; _you_ or _someone else_ for an account without one): each sync replaces the phone's `accounts` table (id and name) with the server's accounts, which every signed-in account can list since `1792800000-account-names.js` (PocketBase still hides another account's email). The recipes from before authors (migration `1792700000-recipe-author.js`) went to the oldest account, the one every phone shared until then; their `updated` moved, not their `modified`, so the phones pull the author without losing a change. |
| Deletions             | The delete queries record the row in `sync_deletions` (same transaction). The push marks it `deleted` on the server, which never removes rows: the other phones see the deletion and delete their copy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Used ingredients      | An ingredient deleted on one phone while a recipe on another uses it is decided once the pull has brought the recipes too: deleted if no recipe there uses it any more (their deletions came with the same sync), else kept and pushed again (a recipe added there since uses it). Deciding before the recipes brought back ingredients deleted along with every recipe using them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Server versions       | Each row keeps the version (`updated_at`) the server has of it, in `server_version`: set when it's pulled, and when a push is saved (`'saved'`, not `'kept-newer'`). A sync pushes only the rows whose `updated_at` differs, so it never sends back what it just pulled. Pushing everything changed since the previous sync started did: a phone sent back every row pulled since, with its own copy of the content, and the server then took an equal version with any content (it no longer does, see _Newest change wins_): on 2026-10-21, a TV with its own "œufs" sent back recipes without their eggs (it had skipped the other phone's "œufs", see _Same-name ingredients_). Connecting to a server clears every `server_version` (everything is pushed once and merged); a phone that synced with an app from before server versions takes the rows changed before its last push (`pushedFrom`) as on the server, and a pulled row of the same version as its own as on the server too.                                                                                                                                                                                                                                                                    |
| Same-name ingredients | A pulled ingredient named like an ingredient here with another sync id (added on two phones with different ids: an older app, or rows written straight into a database) isn't added: this phone keeps its own, and records the other id in `ingredient_aliases`. Recipes pulled with that id link this phone's ingredient. When this phone saves such a recipe, it pushes it with its own id: the server converges to one. When the other id is deleted on the server, its alias stays until the recipes are pulled (a newer recipe may still list it), then goes, and this phone pushes again the recipes linking its own ingredient, so the server's stop listing the deleted one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Same-title recipes    | Titles are unique on each phone, dishes and drinks together, ignoring case and accents (`recipes_sort_key_unique`, see [database.md](database.md)); the server doesn't check them. When a pull would give a recipe the title of another one here (added on two phones before they synced, renamed on one, or merged field by field, see _Changes on two phones_), the recipes titled like it, numbered or not (`crêpes`, `crêpes (2)`…), are numbered again in sync id order: the first keeps `crêpes`, the next is `crêpes (2)`, and so on, each in its own spelling. The same recipes get the same titles on every phone, whatever order they arrived in (`sync-scenarios.ts` syncs three phones in every order). A recipe renumbered here gets a newer version, pushed by the same sync (its `synced_content` keeps the server's title). Both recipes are kept: the user deletes or renames the one they don't want. The recipes that shared a title before titles were unique were numbered the same way by migration `0013_unique-recipe-titles`.                                                                                                                                                                                                             |
| Bad rows              | Rows from the server are checked (id format, non-blank title or name, known season and course; a recipe's kind is a drink only when it says so, else a dish) and skipped or corrected, never trusted blindly.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

### Ids

Integer ids stay on the phone. A row's identity across devices is its `sync_id`: 15 characters of `[0-9a-f]`, the format of PocketBase record ids, so the phone creates records with their final id.

- Recipes and meals: random (SQLite `randomblob`).
- Ingredients: derived from the name (`toIngredientSyncId`, a hash of the name key), so "Leek" added on two phones before they sync is one ingredient. Renaming keeps the id.

### Known limits

- **The same field changed on two phones**: the newest change (by the phones' clocks) wins that field, without a warning; the other fields keep both phones' changes (see _Changes on two phones_). The recipe text is one field: two phones editing different steps keep the newest text.
- **A push racing another phone's**: a phone that pulled, merged and pushes in the same seconds as another phone pushes the same recipe can still replace that one's change, if its version is newer: the server doesn't check what the push started from.
- Times come from each phone's clock: a phone with a clock far off could win or lose against changes it shouldn't. One more than a day ahead gets an error from the server for the rows it changed meanwhile, until the server's clock is within a day of them (setting the phone's clock right stops new ones).
- An ingredient renamed on one phone to a name another phone already uses for a different ingredient keeps its old name on that phone (it isn't merged into that one, nor aliased).
- One server is one shared recipe library: every account sees and can change everything. The author is only for the _Added by_ filter.
- A recipe keeps the author it had on a phone connected to another account or another server later: it's then no longer in that phone's _Mine_. A recipe whose account was deleted on the server keeps it on the phones that had it.
- Deleted rows stay on the server (marked `deleted`), so that phones that haven't synced in a while learn about the deletion.

## Server setup

The PocketBase version in `server/pocketbase-version`, the one the tests run against (never older than 0.34.0: the update rule uses `@request.body.<field>:changed`); a newer one goes through [Upgrading PocketBase](#upgrading-pocketbase) first:

1. Install the server files: `server/migrations/*.js` into `pb_migrations/` and `server/hooks/*.js` into `pb_hooks/`, next to the PocketBase executable, then restart it (`pocketbase serve` applies the migrations). The migrations create the `ingredients`, `recipes` and `cooked_meals` collections with their API rules, close sign-up on `users`, make sign-in tokens last a year (each sync renews it), and limit sign-ins to 5 a minute per account collection (the app's accounts on one side, the admin's on the other; passwords, and one-time codes or OAuth2 if ever enabled; renewing a token and syncing aren't limited); the hooks tell the app the server's version (see [Versions](#versions)), give each recipe its author and refuse versions more than a day ahead. `npm run server:deploy` does all this, and installs the updater that keeps them up to date (see [Updating the server](#updating-the-server)).
2. In the admin UI (`/_/`), create an account in **users** for each person, with their name (shown on the recipes they add), for their phones to sign in with: everyone sees and edits every recipe, and the _Added by_ filter shows each person theirs.
3. Serve it over **HTTPS with a valid certificate**: Android refuses plain HTTP. Any reverse proxy works (e.g. Caddy). Behind it, every client has the proxy's address, so the sign-in limit counts all the clients' sign-ins together (5 a minute for the app's accounts, 5 for the admin's: someone guessing passwords also delays new phones' first sign-in, not phones already signed in); no trusted-proxy header is set, because without a proxy a client could fake its address with it. If the server is reachable from the internet, also keep the admin UI (`/_/` and `/api/collections/_superusers/`) to the home network at the proxy, or with PocketBase's _Settings › Superuser IPs_.
4. Back up `pb_data/` (PocketBase has built-in scheduled backups).

## Web app

The server also serves the app for a desktop browser (the same code, exported with `npm run web:export`), from PocketBase's `pb_public/` folder: open the server's address (`https://recipes.example.org`) in a browser. Its pages go to the app (PocketBase's index fallback), `/api/` and `/_/` stay PocketBase's. The updater installs it with the other server files (see [Updating the server](#updating-the-server)).

- **Its data** is the browser's, like a phone's: an SQLite database (expo-sqlite's web build, WebAssembly, in the site's private file system) and the photos beside it; the sync is optional, and Settings › Data storage offers the server it comes from. The browser is asked to keep the data (`navigator.storage.persist()`), but clearing the site's data deletes it, and a browser that refuses may delete it itself when short of space; the About page says both: syncing keeps a copy. The sign-in token is in the site's `localStorage` (no Keystore in a browser).
- **Headers**: expo-sqlite's synchronous calls (all the app's) need `SharedArrayBuffer`, which browsers give only to a cross-origin isolated page served over HTTPS (or `localhost`). `server/hooks/web-app.pb.js` sends `Cross-Origin-Embedder-Policy: require-corp` (Safari doesn't know `credentialless`; the app loads nothing from other sites) and `Cross-Origin-Opener-Policy: same-origin` on every page but `/api/` and `/_/`: nothing to set in the reverse proxy. expo-sqlite's wait for its worker is patched (`patches/expo-sqlite+*.patch`, applied by `patch-package` on install): it gave up after a count of spins that lasts ~35 ms on a recent Mac, less than opening the database or a migration takes. The browser starts the worker asynchronously before the app's first call (`src/db/web-database.ts`): blocked, the page couldn't start it. Check the patch at each Expo SDK upgrade.
- **What differs from the phone**: files `x.web.ts` next to `x.ts` (Metro picks them in a browser; `src/types/platform-apis.ts` checks they export the same): dialogs (`src/components/alert.web.ts`, react-native-web's `Alert` does nothing), photos (the site's private files), reading a photo or a PDF (Tesseract.js and pdf.js instead of ML Kit and Android's renderer; their workers, engine and English and French data are served from `/ocr/`, copied by `scripts/web-ocr-files.mjs`, never from a CDN), sharing a recipe (the browser's print window, _Save as PDF_), sharing a list (the browser's share sheet, or the clipboard), the token. A browser has no camera to open: photos and pages are files. On a window wide enough for the menu and a screen, the menu stays open on the left, as on a TV (`src/components/use-menu-always-open.ts`).

## Versions

Before each sync, the app asks the server `GET /api/dishes-cook/server` (`server/hooks/server-info.pb.js`, public: nothing secret in it) and compares (`src/features/sync/server-version.ts`):

| The server…                                                       | The app                                                                                                     |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| has every migration this app knows                                | syncs.                                                                                                      |
| lacks the last one (or has no such endpoint: installed before it) | doesn't sync: Settings says the **server** needs an update. Changes wait on the phone.                      |
| asks for a newer app (`minimumAppSyncVersion` > `SYNC_VERSION`)   | doesn't sync: Settings says the **app** needs an update. Changes wait on the phone.                         |
| has migrations this app doesn't know                              | syncs (server changes only add fields, so older apps keep working), and Settings says an app update exists. |

- **A server migration** goes in `server/migrations/`, never edited once merged (checksums in `src/db/frozen-migrations.test.ts`), and in `SERVER_MIGRATION_LIST` (`server-version.test.ts` checks the list matches the folder). From then on, this app version syncs only with servers that have it.
- **A change that breaks older apps** (not just new fields): raise `SYNC_VERSION` in the app and `MINIMUM_APP_SYNC_VERSION` in the hook, in the same PR. The hook's can never be higher than the app's (tested): the app couldn't sync with its own server.

## Updating the server

The server needs the files of the app version the phones run: migrations and hooks, and the web app it serves. Two ways to install them, both through `server/deploy/update-server.sh`:

- It installs only what's new: new migrations, new or changed hooks, and it removes hooks the archive no longer has. The web app (`public/` in the archive) replaces `pb_public/` whole when it differs, owned by root and only readable by PocketBase's user: copied beside it (`pb_public.new`), then swapped in by renames, so an update cut short never leaves it half-copied (the old one set aside in `pb_public.old` is put back by the next run); an archive without one leaves it. The archive may hold only plain files (no links) under `migrations/`, `hooks/` and `public/`, named with letters, digits and `._@+-`; a web app without `index.html` is refused. It never installs an edited migration (it stops instead), nor files older than the installed ones: each archive carries a `VERSION` (commit time and commit), and the installed one is kept in `server-files.version` in the updater's folder (`/var/lib/dishes-cook-update`, or `$UPDATE_STATE_DIR`), so an older release can't undo a manual deploy from `main`. The updater's files live there, root-only, not next to PocketBase: PocketBase's user could otherwise swap them for links or forge the installed version (earlier updaters kept them in PocketBase's folder: the first run moves them). It also refuses `pb_data`, `pb_migrations`, `pb_hooks` or `pb_public` when they're links rather than folders.
- It stops PocketBase, backs up `pb_data/` (`backups-before-update/` in the updater's folder, root-only since it holds the accounts, the last 5 kept), installs the files and starts PocketBase again. On any failure from then on, or if PocketBase doesn't come back healthy, it puts the data and files back as they were and starts it.
- One run at a time (a lock): the timer and a manual deploy can't overlap.

- **Automatically, from releases**: each GitHub release carries `server-files.tar.gz` (`scripts/pack-server-files.sh`, with the web app built by a job of its own, which never gets the attestation's token), its `.sha256`, and its attestation `.sigstore.json`: a signed proof (Sigstore build provenance, in a public log) that the repository's release workflow built it on `main`. The `dishes-cook-server-update.timer` runs the updater every hour: it downloads the latest release's archive, checks its attestation with [cosign](https://github.com/sigstore/cosign) (a pinned version it downloads once, checked against its checksum, into `/usr/local/lib/dishes-cook-update/`), and installs it if there's anything new. An archive without a valid attestation (published by hand, or by anything but that workflow on `main`) is refused: being able to publish a release isn't enough to run code on the server.
- **By hand**, before releases or right away: from an up-to-date `main`, `SYNC_SERVER_SSH=<user@host> npm run server:deploy` builds the web app, packs it with `server/`, copies it over SSH and runs the updater (`sudo` on the server). It also installs or refreshes the updater (`/usr/local/sbin/dishes-cook-update-server`) and enables its timer. It refuses to deploy from anything but an up-to-date `main` without local changes (`FORCE=1` for a test server; the web app is built from the whole checkout): a migration deployed from a branch, then edited before merging, would never reach the server in its final form.

Logs: `journalctl -u dishes-cook-server-update`. Phones show "the server needs an update" until it's done; their changes wait on them meanwhile.

## Testing during development

- **Tests** run against `src/test/fake-sync-server.ts`, which mirrors the behaviours below; `sync-engine.test.ts` simulates two phones.
- **Against a real PocketBase**: `npm run test:pocketbase` runs the same two-phone scenarios (`src/test/sync-scenarios.ts`) and checks the behaviours below on a throwaway PocketBase: the version in `server/pocketbase-version` (or `POCKETBASE_VERSION=0.x.y`), downloaded once into `node_modules/.cache/pocketbase` and checked against the release's checksums, started empty with `server/migrations` on a free local port, and stopped afterwards. CI runs it on every PR. Needs `curl` and `unzip` (macOS or Linux).
- **End to end**: `npm run test:e2e` runs the Maestro flow `.maestro/sync.yaml` (connect, merge, deletion) on an emulator against a throwaway PocketBase; see [.maestro/README.md](../.maestro/README.md).
- **On an emulator**, against a throwaway PocketBase (never your real one, its data would mix with test recipes):
  1. Start one with the migrations: `pocketbase serve --dir /tmp/pb-test/pb_data --migrationsDir server/migrations --hooksDir server/hooks --http 127.0.0.1:8091` (without `--hooksDir`, the app finds no version endpoint and says the server is too old), create a superuser (`pocketbase superuser upsert … --dir /tmp/pb-test/pb_data`), then an account in **users** from its admin UI.
  2. Forward the port to the emulator: `adb reverse tcp:8091 tcp:8091`.
  3. In the app, connect to `http://localhost:8091`. Plain HTTP only works in **debug** builds (they allow cleartext for Metro); release builds need HTTPS.
  4. Add, edit and delete recipes, change rows in the admin UI, and check both sides (Settings shows the last sync).
- **The web app**: `npm run web` serves it in development with the headers it needs (`metro.config.js`), on `http://localhost:8081`; to sync it with a throwaway PocketBase, start that one on `localhost` too (a browser's page and its server: same rules as the phone, HTTPS or `localhost`). The production build: `npm run web:export -- --output-dir dist/web`, then `pocketbase serve … --hooksDir server/hooks --publicDir dist/web`, opened on `http://localhost:<port>`.

## Server behaviour the app relies on

Measured on a real server, and mirrored by the test server (`src/test/fake-sync-server.ts`):

- A refused or expired token is treated as a guest: lists come back **empty** (not 401), creates get a 400, updates a 404. That's why every sync starts by renewing the token (`auth-refresh`), which does fail with a 401.
- An update refused by the update rule (an older change, or the same version with other content) gets a 404; the app then tries a create, which gets a 400 `validation_not_unique` for an existing id: the server keeps its row. An older change is replaced by the server's newer row at the next pull; a same-version conflict isn't (a pull replaces only with a newer version): the phone keeps its content until either side saves a newer version.
- `updated` (`2026-10-14 18:03:59.794Z`) sorts as text in time order: it's the pull cursor.

## Upgrading PocketBase

PocketBase hasn't reached 1.0: a minor version can change its API, its API rules or the JS migrations API. The server runs the version in `server/pocketbase-version`, the one the tests pass with.

1. **Read the release notes** of every version in between ([releases](https://github.com/pocketbase/pocketbase/releases)), looking for breaking changes to the records API, auth, API rules and JS migrations (`Collection`, `migrate`).
2. **Test it first**: on a branch, set the new version in `server/pocketbase-version` and run `npm run test:pocketbase` (CI runs it on the PR too). If something fails, fix the app, or add a server migration (never edit one, see [database.md](database.md#changing-the-schema)), then merge.
3. **Back up `pb_data/`** on the server: stop PocketBase and copy the folder, or make a backup from the admin UI (Settings › Backups) and keep a copy off the server.
4. **Replace the executable** with the new version's, downloaded from its release page and checked against that release's `checksums.txt` (not `pocketbase update`: it installs the latest version, not the tested one). Copy any new file of `server/migrations/` into `pb_migrations/`, then start it: PocketBase upgrades `pb_data/` and applies the new migrations on start.
5. **Check**: the admin UI opens with the collections and their records, a phone syncs (Settings › Data storage › Sync now), and a change made on one phone reaches another.
6. **If anything goes wrong**, stop PocketBase and put back both the previous executable and the `pb_data/` backup: the new version may have changed `pb_data/` in a way the old one can't read.
